# late.sh production deployment lessons for Termon

late.sh is a useful operational comparison because it runs a public, stateful SSH TUI with long-lived sessions, but it is now a much larger system than Termon. The strongest lessons are to preserve Termon's simpler two-container topology, add durable observability and edge-level abuse controls, and test slow-client behavior before load forces a redesign. late.sh does **not** provide evidence that Termon should adopt Kubernetes or abandon SSH/TLS multiplexing.

This report treats the late.sh repository at commit `bec3d9e1b3042a2286d206002ae63f645ec1f111` as a first-party snapshot. “Verified” means an official page, checked-in manifest, workflow, source file, or first-party production note states the fact. “Inference” labels conclusions drawn from those artifacts or live protocol probes. Repository searches found no public runbook for restore drills, SSH host-key rotation, automated rollback, alert routing, or DDoS-provider configuration; those absences are not proof that the hosted service lacks private procedures.

## What late.sh is

late.sh describes itself as a terminal-first social application reached with `ssh late.sh`. It combines chat, music, games, news, profiles, a web frontend, a companion CLI, and several separately hosted “door” games; PostgreSQL holds shared application state, while Icecast/Liquidsoap and LiveKit provide audio and real-time media ([official site](https://late.sh/), [repository overview](https://github.com/mpiorowski/late-sh/blob/bec3d9e1b3042a2286d206002ae63f645ec1f111/README.md#L1-L10)). This makes it a relevant SSH-operations case study, but its media and multi-service requirements explain much of the infrastructure that Termon doesn't need.

## Deployment and operations comparison

| Area | Verified late.sh evidence | Concrete comparison and lesson for Termon |
| --- | --- | --- |
| **SSH ingress and ports** | Public SSH enters on TCP 22 through RKE2's ingress-nginx TCP listener, which forwards to `service-ssh-sv:2222` and prepends PROXY metadata ([TCP manifest](https://github.com/mpiorowski/late-sh/blob/bec3d9e1b3042a2286d206002ae63f645ec1f111/infra/ssh-tcp.tf#L1-L53), [infra overview](https://github.com/mpiorowski/late-sh/blob/bec3d9e1b3042a2286d206002ae63f645ec1f111/infra/README.md#L119-L140)). | Termon similarly keeps the application on unprivileged port 2222 and recovers the client address through PROXY protocol. late.sh additionally restricts accepted PROXY senders to configured CIDRs; Termon now isolates `termond` on a dedicated internal Compose network where `sslh` is its only intended peer. |
| **TLS/SSH multiplexing** | The public manifests assign TCP 22 to raw SSH and normal HTTP ingress/TLS to web hostnames. No checked-in `sslh`, SNI multiplexer, or SSH-on-443 route was found. late.sh warns that cert-manager-triggered ingress-nginx reloads can terminate long-lived SSH workers and proposes moving SSH to a dedicated TCP edge ([documented reload risk](https://github.com/mpiorowski/late-sh/blob/bec3d9e1b3042a2286d206002ae63f645ec1f111/CONTEXT.md#L792-L800)). | Termon's `sslh` design deliberately supports networks that block port 22. Keep it unless usage shows no demand, avoid coupling `sslh` restarts to Traefik reloads, and smoke-test SSH/22, SSH/443, and HTTPS/443 after every edge change. |
| **DNS and proxying** | The setup guide asks for apex and wildcard A records, matching AAAA records for IPv6, and warns that ordinary Cloudflare proxying does not forward required raw media ports ([DNS guidance](https://github.com/mpiorowski/late-sh/blob/bec3d9e1b3042a2286d206002ae63f645ec1f111/infra/README.md#L53-L76)). | Termon's grey-cloud requirement is stricter because the apex carries raw SSH. Keep `termon.sh` DNS-only unless a raw-TCP proxy is explicitly configured and tested. |
| **Runtime topology** | First-party production notes record one Debian 13 RKE2 node with 8 CPU and about 15.6 GiB RAM. It runs one SSH pod, one web pod, separate game/media pods, Redis, and a two-instance CloudNativePG cluster; stateful PVCs use node-local storage ([production inventory](https://github.com/mpiorowski/late-sh/blob/bec3d9e1b3042a2286d206002ae63f645ec1f111/SCALE.md#L7-L45)). | Termon's distroless single binary plus `sslh` is easier to patch, restore, and reason about. Don't import RKE2 or PostgreSQL before independent scaling or failover is required. Multiple database replicas on one node do not remove the host failure domain. |
| **Persistence and backups** | CloudNativePG archives compressed WAL and data to S3-compatible storage, retains it for seven days, and schedules a daily backup at 02:00 ([backup configuration](https://github.com/mpiorowski/late-sh/blob/bec3d9e1b3042a2286d206002ae63f645ec1f111/infra/cloudnativepg.tf#L23-L79), [cluster and schedule](https://github.com/mpiorowski/late-sh/blob/bec3d9e1b3042a2286d206002ae63f645ec1f111/infra/cloudnativepg.tf#L81-L178)). No public restore drill was found. | Termon's stopped-container backup of the whole SQLite volume includes WAL/SHM state and the host key. Its 14-day retention and mandatory restore drill are stronger documented controls. Consider online SQLite backup only when measured downtime becomes unacceptable. |
| **SSH host keys** | Setup generates one Ed25519 key, stores it through a GitHub environment secret and Kubernetes Secret, and mounts it read-only ([key creation](https://github.com/mpiorowski/late-sh/blob/bec3d9e1b3042a2286d206002ae63f645ec1f111/infra/setup_app.sh#L81-L88), [secret persistence](https://github.com/mpiorowski/late-sh/blob/bec3d9e1b3042a2286d206002ae63f645ec1f111/infra/setup_app.sh#L146-L193), [pod mount](https://github.com/mpiorowski/late-sh/blob/bec3d9e1b3042a2286d206002ae63f645ec1f111/infra/service-ssh.tf#L300-L368)). No public fingerprint, rotation, or restore procedure was found. | Keep Termon's key in the backed-up data volume and compare its fingerprint during every restore. Store the expected fingerprint outside the VPS so restoring the volume alone cannot define success. |
| **Observability** | Applications send OpenTelemetry to an in-cluster collector backed by VictoriaMetrics, VictoriaLogs, VictoriaTraces, and Grafana. Dashboards include active SSH sessions, connection/pairing rates, render rates, and slow-client output-budget skips/disconnects ([SSH dashboard](https://github.com/mpiorowski/late-sh/blob/bec3d9e1b3042a2286d206002ae63f645ec1f111/monitoring/dashboards/observability.json#L1038-L1100), [render and stall panels](https://github.com/mpiorowski/late-sh/blob/bec3d9e1b3042a2286d206002ae63f645ec1f111/monitoring/dashboards/observability.json#L1375-L1510)). Production notes quantify per-session CPU/memory and describe collector gaps ([measured follow-up](https://github.com/mpiorowski/late-sh/blob/bec3d9e1b3042a2286d206002ae63f645ec1f111/SCALE.md#L77-L113), [observability gaps](https://github.com/mpiorowski/late-sh/blob/bec3d9e1b3042a2286d206002ae63f645ec1f111/SCALE.md#L612-L619)). | Termon already exposes Prometheus metrics and JSON logs. Exporting privacy-filtered logs to PostHog, retaining the Prometheus endpoint, and adding independent uptime/host monitoring closes the immediate gap without copying late.sh's full stack. |
| **Abuse and overload controls** | Production caps SSH sessions globally and per IP, rate-limits attempts, and trusts PROXY only from explicit CIDRs ([production limits](https://github.com/mpiorowski/late-sh/blob/bec3d9e1b3042a2286d206002ae63f645ec1f111/late-ssh/src/config.rs#L407-L425)). A port-22 flood drove ingress-nginx to about five cores and triggered a four-minute outage; the response added a 3-CPU cap and less brittle probes ([incident-linked controls](https://github.com/mpiorowski/late-sh/blob/bec3d9e1b3042a2286d206002ae63f645ec1f111/infra/ssh-tcp.tf#L17-L53)). After an OOM, late.sh bounded queued output at 32 MiB and disconnects clients stalled for 30 seconds ([incident follow-up](https://github.com/mpiorowski/late-sh/blob/bec3d9e1b3042a2286d206002ae63f645ec1f111/SCALE.md#L77-L113)). | Termon's in-process limits begin after connection acceptance. Add provider/host edge controls and load-test `sslh`, half-open handshakes, authentication bursts, and clients that stop reading. Add an output budget only if the test demonstrates unbounded growth. |
| **Deploy and rollback** | Release workflows run CI, build a component image, update one Deployment, and wait for rollout ([deploy design](https://github.com/mpiorowski/late-sh/blob/bec3d9e1b3042a2286d206002ae63f645ec1f111/.github/workflows/deploy_service.yml#L1-L18), [rollout steps](https://github.com/mpiorowski/late-sh/blob/bec3d9e1b3042a2286d206002ae63f645ec1f111/.github/workflows/deploy_service.yml#L143-L172)). SSH uses `maxSurge: 1`, `maxUnavailable: 0`, and a six-hour termination grace period ([rollout strategy](https://github.com/mpiorowski/late-sh/blob/bec3d9e1b3042a2286d206002ae63f645ec1f111/infra/service-ssh.tf#L1-L38)). No automatic rollback or database compatibility gate was found. | Preserve Termon's schema/Save compatibility and restore-based rollback contract, but deploy a prebuilt digest-pinned image and automate post-deploy protocol checks. Graceful draining should wait until termond can reject new sessions while allowing active Battles to finish. |

## Recommended actions for Termon

1. **Export existing operational signals.** Send privacy-filtered structured logs to PostHog, retain the Prometheus endpoint, and add independent uptime and host-resource monitoring. Alert on readiness, persistence failures, restarts, disk pressure, backup age, and stale monitoring.
2. **Load-test the edges, not only Battles.** Cover connection floods through `sslh`, half-open handshakes, repeated authentication attempts, and clients that stop reading. Record CPU, memory, queue growth, readiness, and recovery.
3. **Narrow PROXY trust explicitly.** Keep port 2222 unpublished and place `termond` on a dedicated internal network reachable only by `sslh`; verify network membership during deployment.
4. **Automate the current runbook.** Deploy a content-addressed image, run readiness plus SSH/22, SSH/443, HTTPS/443, Trainer-load, and completed-Battle checks, and retain the previous digest and backup ID together.
5. **Keep the present persistence model.** One SQLite volume and stopped backups fit Termon while scheduled downtime is acceptable. Revisit only when recovery objectives become product requirements.

## Tradeoffs and evidence limits

late.sh's architecture buys component isolation, rolling application updates, online PostgreSQL backup/WAL archiving, and rich telemetry. It pays with a larger patching surface, several stateful systems, node-local storage constraints, and operational coupling through one current cluster node and shared ingress. Its scale notes also say SSH cannot safely scale horizontally yet because session and paired-WebSocket ownership remain process-local; Kubernetes cannot remove application-level affinity requirements.

The live probes support only a narrow observation: late.sh served a russh SSH banner and Ed25519 key on TCP 22, while TCP 443 completed TLS for a Let's Encrypt certificate and did not return an SSH banner. This matches the manifests but cannot prove that no private route exists.
