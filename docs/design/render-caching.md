# Render caching and SSH output

## Bounded session output — TERM-70

Termon keeps authoritative updates separate from terminal delivery. One
`sessionoutput.Writer` worker owns each session's gameplay output stream. The
application retains at most 256 KiB of pending payload, **including the active
write**. This is not a bound on the peer's SSH receive window, kernel TCP buffers,
terminal cell buffers, or total session memory.

While any output is pending, cosmetic ticks still advance model state and return
their commands, but defer frame construction. The next unpressured tick paints the
latest state once. Direct input, resize, errors, Save updates, and other Hub
messages bypass this cosmetic gate. Their updates retain their existing order;
no Hub messages, Battle commands, persistence operations, or Battle playback
state are discarded by the gate. Bubble Tea can still merge Views arriving within
one renderer interval, as it did before this policy.

ANSI output already generated by the renderer remains FIFO and is never replaced
with a newer delta. Replacing deltas would invalidate the renderer's terminal
state. A write that cannot fit the budget, a write error, or a channel write that
fails to complete within 10 seconds closes the SSH **transport**. Closing the
transport also releases a write blocked on TCP; attempting to send a channel-close
packet cannot guarantee that. Other channels multiplexed on that transport close
with it. Cancellation joins the worker and releases queued bytes. Normal Program
completion drains accepted bytes and joins the worker without closing a healthy
shared transport; the worker's lifetime is the shell channel, not the connection.

Disconnection is not successful feedback delivery. A disconnected Trainer can
miss transient visual feedback, but committed Saves and Battle Results remain in
SQLite and the existing active-Battle reconnect grace still applies. The policy
does not promise delivery to a client that isn't reading. It prevents that client
from holding the renderer mutex and delaying later Hub broadcast recipients.

The 256 KiB budget permits bursts larger than the measured 120×40 frames without
allowing indefinite growth. The 10-second whole-write deadline is deliberately
far above the measured healthy write durations (almost all below 1 ms; all below
20 ms in the one-session matrix), while a 1 KiB/s reader completed its roughly
4 KiB animation writes without disconnecting. These are initial operating bounds,
not a claim that a 10-second response is playable. Revalidate for larger PTYs and
slower links before changing them.

The 100 ms model tick, authoritative Hub tick, and default 60 FPS renderer remain
unchanged. See the [measured diagnosis](../ssh-session-latency.md) and
[reproduction procedure](../load-baseline.md#in-session-latency-and-output-pressure).

## Ordinary idle-frame invalidation — TERM-71

Onboarding invalidation follows existing visual edges rather than rebuilding at
every logical tick. Typewriter progress still paints every tick while text is
incomplete; idle poses and prompt/cursor blinks paint at their existing boundaries.
Settled dialogue and handle selection are static. Input and Hub feedback still
invalidate immediately, and no animation clock or duration changes. Full-repaint
comparison tests guard every onboarding stage against skipped visible changes.

This reduces construction and allocation work, not animation traffic: Bubble Tea
already discarded identical frames later. Battle invalidation remains conservative
until its independent clocks and playback transitions have equivalent coverage.
See the [follow-up measurements](../render-latency-followup.md).

## Component-level caches for busy frames

Follow-up finding from the sustained idle-render profile (see
`load-baseline.md`). Status: **not scheduled** — build when busy-frame
measurements justify it.

## Problem space

Frame memoization (`internal/tui/model.go`, dirty-flag invalidation) removed
idle-render cost: settled screens rebuild nothing between messages. What
remains is **busy-frame** cost — frames that legitimately change every tick:

- a lobby where several Trainers walk at once,
- Battle playback (typing/shake/faint animation, idle-pose alternation).

On those frames `buildFrame` still recomposes and re-measures the entire
frame each tick even though most of its content is identical to last tick.
The post-memoization profile attributes roughly half the remaining CPU to
exactly this: `tui.Model.Update`/`buildFrame` (~35% cum),
`x/ansi.stringWidth` (~22% cum), `lipgloss.Style.Render` (~11% cum).

## Design sketch

Cache rendered pieces, not whole frames. Every expensive sub-component
produces `(ansiString, width)` pairs keyed by a cheap input tuple:

| Component | Cache key | Width source |
|---|---|---|
| Sprite block | species slug × facing × pose frame | fixed art grid — known at load time, never measure |
| Lobby Trainer block | handle + species + emote + walk-frame | measured once per key |
| Floor layer | already cached (static) | cached alongside |
| Chrome wrapper | width × height | arithmetic, not measurement |

Composition then concatenates cached strings and **sums cached widths**;
`stringWidth` runs only on pieces that actually changed. The existing
event-log cache (`evCache`) is the precedent to follow.

Invalidation stays explicit like `frameDirty`: walkers carry a walk-frame
counter; battle animation state already derives from `battleAge`; nothing
keys on wall-clock time.

## Measurement gate — build only if triggered

Re-run the sustained-profile procedure while driving movement (harness sends
no keystrokes today, so a walking-lobby scenario needs either harness keys or
a scripted multi-client driver). Build this only if a busy lobby at realistic
population still shows `buildFrame`+width-measurement above ~100% of one core
at 512 sessions. Idle cost is already solved and must not regress: the
memoized fast path must stay allocation-free (assert via the frame tests'
`frameBuilds` counter plus an allocations check).

## Out of scope when built

Upstream renderer changes (bubbletea/ultraviolet diffing is not the
bottleneck), sprite pipeline changes, protocol changes.
